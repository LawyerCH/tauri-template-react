# 开发流程

目标是让 AI 每次都走同一条可验证的路，而不是每次即兴发挥。六个阶段，每个阶段有明确产物和退出条件。

## 1. 理解

先判断意图类型，不同意图走不同深度：

| 类型 | 判定信号 | 深度 |
|---|---|---|
| 新建 | "加一个""做个" | 完整六步 |
| 修改 | "改成""调整" | 三步：理解 → 实现 → 验证 |
| 修复 | "报错""不对""没生效" | 先复现，再定位，最后改 |
| 探索 | "有没有办法""能不能" | 只调研，不改代码 |
| 咨询 | "这是什么""怎么用" | 直接回答，不碰文件 |

必须问清三件事，缺一件就停下来问（一次问完，不要挤牙膏）：

1. **谁用**：目标角色与使用场景
2. **失败怎么办**：异常、空数据、无权限时的表现
3. **怎么算做完了**：可观察、可演示的验收条件

不要替用户发明需求。找不到先例又无法确认时，给 2–3 个方案 + 推荐，等选择。

## 2. 定规格

新建类改动写 `specs/NNNN-<name>.md`（模板见 `specs/_template.md`）。规格里最有价值的是**验收标准**和**非目标**：

- 验收标准写成可执行句子："点击 X 后 Y 出现，且刷新后仍存在"
- 非目标明确写出"本次不做"，防止范围蔓延

修改类可以省掉文件，但验收条件必须落在对话里。

## 3. 拆任务

按层拆，顺序固定：类型/契约 → 逻辑 → UI → 测试。

- 每步可独立验证，失败能回滚到上一步
- 一步超过 5 个文件或 200 行，继续拆
- 先做能被验证的那部分，不要先铺 UI

## 4. 实现

- 改前先读目标文件与相邻测试；找一个已有同类实现照着写
- 复用现有组件与工具，不新造轮子；`src/components/ui` 里的能覆盖就不写新的
- 只在被两处以上复用时才提取抽象
- 不写"以后可能用到"的开关、参数、兼容层

## 5. 验证

| 改动范围 | 必须做 |
|---|---|
| 纯前端 | `pnpm check` |
| 涉及 Rust | `pnpm check` + `pnpm check:rust` |
| 涉及 UI | 上面 + 浏览器实测：浅色/深色、窄屏、键盘 Tab |
| 涉及打包配置 | 上面 + `pnpm tauri build` |

验证要看真实结果：跑命令、看输出、截图。不要用"应该没问题"代替。

## 6. 交付

见 `docs/quality.md` §交付与发布。核心是：只提交本次相关文件，提交信息说清"为什么"，推送前确认分支。

## 修复类改动的额外要求

1. 先复现：给出触发路径或失败测试
2. 再定位：找到根因，不要只压症状
3. 后修复：能加测试就加一个能复现原问题的测试
4. 同一思路最多试一次，第二次失败就换路径并说明

## 上下文加载策略

默认只读 `AGENTS.md` + 目标文件。按需加载，不要一次把 `docs/` 全读进来：

- 第一次改某个领域 → 读对应 `docs/*.md`
- 已有 spec → 只读该 spec 的相关段落
- 报错 → 只贴失败的那一条，不贴整屏日志

## 什么时候必须停下来问

- 需求缺"失败怎么办"
- 两种实现都合理且代价不同
- 需要新依赖、新权限、改公共 API
- 发现现有代码与文档/规格冲突
