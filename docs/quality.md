# 质量与交付

## 审查五轴

审查不是"看着还行"，按五轴逐条过，只报可验证的问题。

### 1. 正确性

- 边界：空数组、空字符串、超长文本、0 条 / 1 条 / 多条
- 异步：失败分支有没有 UI；重复点击会不会重入
- 状态：刷新后该留的还在吗；切语言/主题后状态是否错乱
- 类型：有没有 `any`、非空断言、吞掉的 `catch`

### 2. 契约

- 前后端字段名、可空性、单位一致
- Rust 命令改名后，前端调用与类型是否同步
- settings 新增字段有没有默认值与非法值兜底
- 新增 capability 是否只开了必要权限

### 3. 可访问性

- 键盘能走完全流程（Tab / Enter / Esc）
- 焦点环可见，不裸写 `outline: none`
- 图标按钮有 `aria-label`，表单控件有可读 label
- 对比度达标（正文 ≥ 4.5:1）

### 4. 性能

- 列表渲染有没有无谓重渲染；依赖数组是否完整
- 大文件/大列表是否需要虚拟化
- 打包产物体积有没有异常增长（看 `vite build` 输出）

### 5. 安全

- 不提交密钥、`.env`、本地路径
- 外部输入（文件、URL、剪贴板）在边界处校验
- 不开不必要的插件权限
- 渲染外部内容不直接注入 HTML

## 审查输出格式

```
阻塞（必须改）：<问题> — <文件:行> — <建议>
建议（可后续）：...
通过：<已检查的轴>
```

- 阻塞项只包含会导致错误行为、数据丢失、安全问题、规范硬违约的内容
- 风格偏好不算阻塞；不确定就标"建议"
- 不给"全面重写"类建议，除非现状无法局部修复

## 提交规范

格式：`<type>(<scope>): <祈使句描述>`

| type | 用于 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修缺陷 |
| `refactor` | 不改行为的重构 |
| `style` | 只动样式/格式 |
| `docs` | 文档 |
| `test` | 测试 |
| `chore` | 工程配置、依赖 |
| `build` / `ci` | 构建与流水线 |

规则：

- 一次提交只做一件事；重构与功能分开
- 提交前只 `git add` 本次相关文件，不用 `git add -A`
- 破坏性变更在 footer 写 `BREAKING CHANGE:`
- 提交前必须跑过 `pnpm check`（涉及 Rust 加 `check:rust`）

## 交付与发布

- 分支：`feat/<短名>` / `fix/<短名>`，不直推 `main`
- 双托管：`origin` → GitHub，`cnb` → CNB；推送两边都推
- 需要构建时先问一句"发布到 CNB 构建吗"
- 发版三处版本号必须同步：`package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`
- 打 tag 与版本号一致：`v0.2.0`
- 自动更新需要签名密钥，密钥不进仓库

## 绝不

- `git push --force`（除非用户明确要求，且不是 main）
- 提交 `.env`、密钥、`src-tauri/target`、临时截图
- 用"已修复"代替证据；必须有命令输出或截图
