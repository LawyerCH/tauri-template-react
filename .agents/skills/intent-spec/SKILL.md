# 意图识别与规格

目标：在写第一行代码之前，把"做什么"和"怎么算做完"钉死。

## 步骤

### 1. 归类

| 类型 | 信号 | 动作 |
|---|---|---|
| 新建 | "加一个""做个" | 走完整流程，产出 spec |
| 修改 | "改成""调整""换成" | 只确认验收条件，不写 spec |
| 修复 | "报错""不对""没生效" | 先复现，转修 bug 流程 |
| 探索 | "有没有办法""能不能" | 只调研出方案，不改实现 |
| 咨询 | "这是什么""怎么用" | 直接答，不碰文件 |

归类错了后面全错。拿不准时按"新建"处理并说明理由。

### 2. 补齐三要素

必须搞清楚：**谁用**、**失败时怎么办**、**怎么算做完了**。

- 能从代码、文档、上下文推断的，自己查，不要问用户
- 推断不了的，一次问完（最多 3 个），每个给 2–3 个选项并标推荐
- 不要挤牙膏式提问，也不要为了显得严谨把能查的东西拿去问

### 3. 写规格

新建类改动写 `specs/NNNN-<name>.md`，用 `specs/_template.md`。核心是两段：

- **验收标准**：可执行句子。"点保存后列表出现新条目，刷新后仍在"
- **非目标**：本次明确不做什么，防止范围蔓延

### 4. 自检

- [ ] 每条验收标准都能当场演示
- [ ] 非目标写了至少一条
- [ ] 涉及新依赖 / 新 Tauri 插件 / 新权限吗？涉及就先说明代价
- [ ] 有没有两种做法都合理？有就摆出来让用户选，不替他决定

## 歧义与冲突

发现需求与现有代码/文档冲突时，不要静默选一个。列出：

```
冲突：需求说 X，现有实现是 Y（文件:行）
A) 按需求，代价…
B) 按现状，需要改需求…
C) 先只做调研，不动代码
→ 选哪个？
```

## 输出

先给结论一句话，再给 spec 路径与关键验收点。不要整篇复述。

## 禁止

- 验收标准里出现"大概""尽可能""体验好"
- 猜需求然后直接开工
- 为不确定的未来加开关、配置项
- 一句话咨询也启动六步流程
